# Orbit social prototype: architecture decision

Reviewed 2026-11-08. No paid service, wallet funding, on-chain transaction or permanent storage promise is authorized. Protocol support and a provider's operational service are different things.

| Candidate | Identity / integration | Messaging, devices, offline behavior | Media / cost / portability |
|---|---|---|---|
| **Nostr NIP-17 + Blossom (selected)** | Rust Nostr SDK; independent secp256k1 communication identity. Ethereum ownership is explicitly linked by a peer-verified SIWE challenge, never inferred from an address. | NIP-44 encrypted, NIP-59 gift-wrapped DMs; relay storage can deliver after reconnection if retained. No universal retention/SLA. Invitations and accepted friendships are Orbit application semantics. Small groups possible later; no built-in MLS key rotation. Key export migrates identity; local encrypted backup preserves contacts/history. | Separate encrypted blobs, SHA-256 addresses and replaceable HTTP storage. BUD-02 is a complete PUT, not a resumable upload guarantee; downloads can resume if byte ranges are supported. Existing public relays and Blossom providers exist, with their own restrictions. No protocol-level free quota. nostr.build currently advertises a 20 MiB free-upload limit; this is not suitable for arbitrary GB video. MIT Rust SDK; draft NIPs/BUDs require compatibility work. |
| **XMTP + external attachment storage** | Wallet-compatible identity with separate installation keys; Rust core and TypeScript SDK. | DMs/groups and established encrypted device/session management. A deployment/network is required; storage/retention follow its operator, not the wallet. MIT libxmtp core, actively maintained SDK ecosystem. More infrastructure/SDK operational surface than this prototype needs. | Remote attachments carry encrypted-file retrieval metadata, not free hosting. Current operator attachment storage defaults to 100 MiB encrypted envelopes and configurable bounds, so overhead matters. S3-compatible hosting incurs provider costs. Good option if an operator budget emerges. |
| Matrix | Mature Rust SDK, device verification and encrypted rooms; Matrix identity separate from wallets. | Mature DMs/groups/history/receipts and federation. Homeserver/account registration required. Public homeserver policies and limits vary. Self-hosting still needs an operator. | Mature media repository and encrypted-file messages; server advertises maximum upload size. Not unlimited; hosting and retention depend on homeserver. Strong alternative when federation is more valuable than wallet interoperability. |
| Waku | Communication network, not bulk-file storage. | Useful transport primitives; application membership, delivery and storage semantics still needed. | Attachments still need external storage; no universal persistent offline delivery or free bulk hosting. |
| Grove / IPFS-compatible storage | Possible replaceable attachment backend, separate from messaging. | Does not replace identity/friendship/message transport. | Provider pinning, gateway access, deletion and pricing must be checked for the specific deployment. No free or permanent availability claim is established here. |
| Autonomi | Optional future archival tier. | Not a live-conversation transport. | Paid uploads and the inability to promise deletion are a poor default for private chat attachments. No integration or transaction in this phase. |

Licenses were checked in the upstream [Rust Nostr SDK](https://github.com/rust-nostr/nostr/blob/master/LICENSE) and [libxmtp](https://github.com/xmtp/libxmtp/blob/main/LICENSE) sources; both use MIT. Protocol specifications and individual providers have separate terms.

## Selected implementation boundaries

- Stable Orbit ID is a Nostr public key, with an independent private communication key protected by Windows Credential Manager. The wallet key is separately generated and protected. A wallet is optional and may have zero balance.
- SIWE challenges belong to the actual verifier, expire, are consumed once, and bind the wallet, communication identity and verifier URI. Connecting an extension or supplying an address does not create a verified mapping.
- Network use is explicit. Invitations contain the recipient's inbox relay choices. Relays may learn recipient public keys, client IPs, sizes and timing despite content encryption. Friendship is a separate accepted state; public following is not treated as friendship.
- `queued` means local outbox; `sent` means at least one recipient relay acknowledged storage; `delivered` requires an encrypted acknowledgment from the recipient application. No read receipt or permanent offline delivery is implied.
- Attachments are encrypted before storage, with keys carried only inside encrypted messages. Plaintext media is cached locally for playback after full verified retrieval. No private file is uploaded merely because it was selected. Provider, encryption, limits and availability are shown before Send.
- The storage boundary is replaceable. Upload resumption is not invented for BUD-02; a canceled/interrupted PUT retries from the start. Download resumption is used only when the server supports valid ranges.
- Backups are encrypted. Wallet recovery alone does not restore messages, friendships, communication keys or unavailable media. An Orbit backup must preserve those independent records; media availability still depends on cached originals or a live provider copy.
